# 爱快（iKuai）的分流为什么更准？

结论先说：**它准的主要原因不是分流算法更强，而是它在 DNS 层就把分流做完了。**

mwan3 生态（包括本项目）做的是"事后纠正"——流量发出前按目标 IP 归属选线路。而 iKuai 做的是"事前决定"——让 DNS 查询从对应线路出去，CDN 自然返回该运营商的最优节点。后者从源头消除了跨网访问，前者只能在既成事实上打补丁。

以下机制均引自爱快官方文档。

---

## 一、核心机制：多线路 DNS

爱快官方对「多线路DNS」的说明：

> 此功能针对多条外网线路设置对应 DNS 地址，使用不同的 DNS 数据包经过不同外网出去的时候**强制使用对应线路设置的 DNS** 做域名解析工作。

配合「域名分流」的强制要求：

> **域名分流必须配合多线路 DNS 配置**
> ① 域名分流线路故障；② 没有设置多线路 DNS —— 都是域名分流不生效的常见原因。

它解决的是这样一件事：

```
访问 bilibili 的 CDN
  走电信线 + 电信 DNS  ->  CDN 返回电信节点  ->  同网直达，快
  走联通线 + 联通 DNS  ->  CDN 返回联通节点  ->  同网直达，快
  走联通线 + 电信 DNS  ->  CDN 返回电信节点  ->  跨网，慢 100 倍
```

第三行正是你报告里 `mcdn.bilivideo.cn` 联通只有 0.04-1 MB/s 的成因——**不是线路差，是解析出的节点不对**。

### 一个容易被忽略的细节

官方特别说明：

> 如果同时使用 DNS 代理服务器和多线路 DNS 功能，**多线路 DNS 内仅默认网关所在策略生效**。因为代理模式下，路由器本身作为源终端去进行 DNS 解析，路由器本身不受任何规则限制，数据都是从默认网关发出。

也就是说：**路由器自身发出的 DNS 查询天然只会走默认路由**，除非你用策略路由单独处理。这解释了为什么"只在路由器上配了两个 DNS"没有效果。

---

## 二、第二层：DPI 应用识别

> 基于 DPI 的流量识别机制……配合**持续更新的 3200+ DPI 特征库**。

> 支持基于源/目的 IP、**域名**、**应用协议** 方式对外网流量灵活调度。

它的价值在于：能按"这是 B 站视频"而不是"这是发往 1.2.3.4 的流量"来决策。当同一个应用的 CDN 节点散布在多个运营商时，按 IP 分永远会分错一部分，按应用分不会。

---

## 三、第三层：粘滞策略与优先级

### 优先级顺序（官方原文）

> 静态路由 > 域名分流 > 端口分流 > 协议分流 > 多线负载 > 默认网关

注意 **域名分流排在端口/协议之前**——这跟我们 `isp-split` 把运营商规则插在端口规则之前的思路一致。

### 7 种负载模式

> 实时连接数、新建连接数、实时流量、**源IP+目的IP**、**源IP+目的IP+目的端口**、源IP、源IP+源端口

官方建议：

> 如果想访问某个协议、某个网站、某个 IP 的时候只会走一条线路，那一定要使用 **源IP+目的IP** 分配或者源IP+目的IP+目的端口分配的模式。

这和 mwan3 的 `sticky` 是同一目的——但 mwan3 的 sticky 只按**源 IP** 粘滞，iKuai 能按**源IP+目的IP** 粘滞，粒度更细，所以同一个客户端访问不同站点时不会被迫全走一条线。

---

## 四、对比：iKuai vs 本项目

| 维度 | iKuai | isp-split（mwan3-nft） |
|---|---|---|
| 运营商 IP 库 | 商业库，含 CDN 供应商归属 | ispip.clang.cn（APNIC 派生），10 类 |
| **DNS 层分流** | ✅ 多线路 DNS，按线路选 DNS | ❌ **没有，这是最大差距** |
| 域名分流 | ✅ 最多 255 条规则 | ⚠️ mwan3 原生支持 `domain`+nftset，但本项目没提供配置入口 |
| 应用识别 | ✅ DPI 3200+ 特征库 | ❌ 只做 L3/L4 |
| 粘滞粒度 | 源IP+目的IP(+端口) | 源IP（mwan3 sticky） |
| 实测反馈 | ❌ 无 | ✅ `probe` 分线测速（但未闭环） |
| 成本 | 商业授权 | 免费开源 |

**差距集中在 DNS。** 其余几项里，域名分流是"有一半能力但没接出来"，应用识别我们做不了也不该做。

## 五、本项目该补什么

按投入产出排序：

### 1. 多线路 DNS（已实现：`isp-split dns`）

思路与爱快一致，但要落在 OpenWrt 的机制上：

```sh
# 给每条线路配一个 DNS
WAN1_DNS=114.114.114.114     # 电信
WAN2_DNS=119.29.29.29        # 联通

# 用 nftables 把发往该 DNS 的 53 端口流量打上对应策略的 mark
nft add rule inet mwan3 mwan3_rules ip daddr $WAN1_DNS udp dport 53 jump mwan3_policy_wan_only
nft add rule inet mwan3 mwan3_rules ip daddr $WAN2_DNS udp dport 53 jump mwan3_policy_wanb_only

# dnsmasq 侧按域名指定用哪个 DNS
# /etc/dnsmasq.conf
server=/bilivideo.com/114.114.114.114
```

**实现方式（已落地）**：不依赖 nft 打标，改用 dnsmasq 的 `server=/域名/IP@接口` —— `@接口` 会用 `SO_BINDTODEVICE` 直接把查询绑到该接口。但需要在 `inet mwan3 mwan3_output` 链顶部给这些 DNS 服务器加 `return`，否则 mwan3 会按目标 IP 重新打标把查询抢走。实测 `mwan3_output` 的钩子是 `type route hook output priority mangle + 1`，确实覆盖本机发出的流量。

### 2. 域名集配置入口

mwan3-nft 原生支持：

```
config ipset
    option name 'bilibili'
    list domain 'bilivideo.com'
```

由 dnsmasq 在解析时自动把结果写进 nftset，再被规则引用。我们只需要在 `isp-split.conf` 里加一段域名组配置，`wire` 时一并生成——**不用改 mwan3**。

### 3. probe 闭环

已有 `probe` 能分线测速，但结果要人工抄回配置。下一步是让它自动改 `ISP_TABLE`（带滞回，避免抖动）。

### 4. 不做的事

- **不做 DPI**：nftables 无法解析到 L7，TLS SNI 偏移不固定也无法用固定偏移匹配。硬做要么上 userspace 抓包（性能崩），要么不靠谱。
- **不做商业 IP 库**：继续用 ispip，同时支持用户换源。

---

## 六、一句话总结

爱快不是"分流算法好"，是**把 DNS 也纳入了分流决策**，让 CDN 主动把最优节点送到你面前。我们现在只做了后半段：IP 归属 → 选线路。补上 DNS 这一环，才真正追平。
